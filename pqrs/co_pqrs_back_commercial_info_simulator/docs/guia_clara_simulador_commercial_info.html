Como funciona el modulo simulador de commercial_info

Este documento explica de forma simple y precisa como el simulador decide que JSON retornar, y que ajustes debes hacer para conectarlo con co_pqrs_back_data.

Modulo: co_pqrs_back_commercial_info_simulator Tipo: FastAPI Comportamiento: igual al mock actual + filtro por apellido

1) Que problema resuelve

Simula el endpoint de burós para entregar respuestas JSON de forma controlada durante pruebas.

Permite tener multiples escenarios en archivos y elegir uno segun los parametros del request.

Fuente de validacion de burós: llamada HTTP/API al simulador.

Fuente de validacion 3270: Postgres (tabla ada_info_detail) en co_pqrs_back_data.

2) Endpoint que expone

Endpoint Metodo Uso
/health GET Verificar que el simulador esta arriba.
/risks/v0/commercial-information GET Retorna el JSON del escenario seleccionado.

3) Como elige el JSON (regla de negocio)

Parametros esperados en query:

identityDocument.documentType identityDocument.documentNumber customer.lastName
  1. Busca coincidencia exacta por documentType + documentNumber + lastName.
  2. Si lastName no llega informado, busca por documentType + documentNumber.
  3. Si no hay match valido, retorna el JSON default.
El indice de escenarios vive en data/scenario_index.json. Ese archivo define los matches exactos, los fallbacks por documento y el archivo default.

4) Archivos clave del simulador

Archivo Responsabilidad
src/infrastructure/entrypoint/fastapi_app.py Expone los endpoints y delega la resolucion.
src/application/scenarios/resolver.py Implementa el orden de busqueda de escenarios.
data/scenario_index.json Mapa de reglas para elegir archivo JSON.
data/commercial_info_*.json Payloads reales de prueba.
data/commercial_info_default.json Fallback cuando no hay coincidencia.

5) Ajustes para usarlo en co_pqrs_back_data

Debes cambiar configuracion para que burós salga por HTTP/API al simulador:

COMMERCIAL_INFO_SOURCE=api COMMERCIAL_INFO_OVERVIEW_URL=http://localhost:8050/risks/v0/commercial-information COMMERCIAL_INFO_API_VERIFY_SSL=false

Y conservar 3270 en Postgres:

CUSTOMER_IDENTITY_SOURCE=postgres POSTGRES_CUSTOMER_IDENTITY_TABLE=ada_info_detail
Importante: el cliente actual de co_pqrs_back_data pide ticket tsec antes de llamar overview. Este simulador (version actual) solo implementa commercial-information. Por eso tienes dos opciones: 1) mantener COMMERCIAL_INFO_TICKET_URL apuntando al mock de ticket existente, o 2) extender este simulador con el endpoint de grantingTicket.

6) Ejemplos rapidos de curl

Match exacto:

curl -G "http://localhost:8050/risks/v0/commercial-information" \ --data-urlencode "identityDocument.documentType=01" \ --data-urlencode "identityDocument.documentNumber=000001069759414" \ --data-urlencode "customer.lastName=gutierrez"

Sin match (cae a default):

curl -G "http://localhost:8050/risks/v0/commercial-information" \ --data-urlencode "identityDocument.documentType=99" \ --data-urlencode "identityDocument.documentNumber=111111111111111" \ --data-urlencode "customer.lastName=no-existe"
