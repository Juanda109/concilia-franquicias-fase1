1. GET /api/v1/jornadas/actual

Quién lo llamaFrontend, automáticamente al entrar a Estado.
Qué recibeNo recibe body ni fecha. Solo headers corporativos cuando se definan.
Qué debe hacer BackendIdentificar la jornada vigente y devolver el resumen ya calculado.
Tabla principalCON_JORNADA.
Campos mínimosidJornada, fechaContable, estado, archivosEsperados, archivosRecibidos, archivosProcesados, archivosPendientes, totalRegistros.
Qué NO debe hacer FrontNo contar filas para recalcular KPI. Los KPI vienen del Backend.
Front
  └─ GET /api/v1/jornadas/actual
       └─ Backend
            └─ CON_JORNADA
                 └─ 200 Jornada JSON
                      ├─ encabezado.fecha = fechaContable
                      ├─ badge = estado
                      ├─ KPI esperados = archivosEsperados
                      ├─ KPI recibidos = archivosRecibidos
                      ├─ KPI procesados = archivosProcesados
                      └─ KPI registros = totalRegistros

2. GET /api/v1/jornadas?fechaContable=YYYY-MM-DD

Quién lo llamaFrontend cuando el usuario cambia el calendario.
ParámetrofechaContable, obligatorio, formato ISO YYYY-MM-DD.
200Existe jornada para esa fecha. Front reemplaza toda la información visible.
204No existe jornada. No hay JSON body. Front abre modal informativo.
ReglaNo confundir 204 con archivos pendientes.
SELECT jornada
FROM CON_JORNADA
WHERE FECHA_CONTABLE = :fechaContable

¿Existe?
  SI  → 200 + Jornada
  NO  → 204 sin body

3. POST /api/v1/jornadas

Quién lo llamaOrquestación batch / Control-M. No el usuario de la pantalla.
EntradafechaContable, tipoEjecucion=AUTOMATICA, origenEjecucion=CONTROL_M.
PersistenciaCrea/controla CON_JORNADA con ARCHIVOS_ESPERADOS=10.
201Jornada creada.
409Ya existe una jornada para esa fecha; evita duplicación.

4. GET /api/v1/archivos?fechaContable=YYYY-MM-DD

Este es el endpoint central de Estado. No debe devolver solamente los archivos recibidos. Debe devolver el inventario funcional completo de 12 posiciones.
CON_INSUMO_ESPERADO (10)
          │
          │ LEFT JOIN por tipo/fuente + jornada/fecha
          ▼
CON_ARCHIVO_CARGA (lo realmente recibido)
          │
          ▼
Resultado de 12 posiciones
          ├─ recibido → idArchivo/nombre/registros/estados
          └─ no recibido → idArchivo=null + estadoRecepcion=PENDIENTE
200La jornada existe. Puede contener 10/10, 8/10, errores, reintentos, expirados, etc.
204No existe información/jornada para la fecha.
OrdenUsar ORDEN_VISUAL de CON_INSUMO_ESPERADO.
CAITNo pertenece al MVP1 y no debe aparecer.
TécnicosPMPD1322 y PMRD8000 tampoco aparecen como filas funcionales.

5. GET /api/v1/archivos/{idArchivo}

ObjetivoExplicar qué pasó con un archivo concreto, no mostrar su contenido transaccional.
ConsultaCON_ARCHIVO_CARGA + CON_CONTROL_ARCHIVO + CON_TRAZABILIDAD y referencia a reproceso cuando aplique.
Debe devolverEstados por etapa, intentos, reprocesos, motivo, fechas, correlationId, controles e historial.
200Archivo encontrado, incluso si está en ERROR_*.
404El identificador no existe.

6. GET /api/v1/archivos/{idArchivo}/contenido?page=0&size=30

ObjetivoMostrar al usuario los registros procesados del archivo sin abrir el archivo físico.
Precondicióndisponible=true y estadoDisponibilidad=DISPONIBLE.
Origen de datosHost → CON_HA22_RESULTADO / CON_HA26_RESULTADO / CON_HA32_RESULTADO. Franquicias → tablas de resultado especializadas por insumo.
Paginaciónpage base 0; size default 30, máximo 100.
200Devuelve contenido y metadatos de paginación.

11. Checklist para desarrollar una fila de Estado

Una fila está correctamente implementada si: aparece aunque esté pendiente; respeta ORDEN_VISUAL; muestra fuente/tipo; presenta nombre/registros solo cuando existen; representa los cinco estados; muestra motivo cuando aplica; conserva correlationId en detalle; habilita contenido únicamente con disponible=true; y nunca convierte un ERROR_* funcional en un error HTTP del GET de inventario.
